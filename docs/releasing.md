# Releasing, rollback and backups

*Status: planned. Steps marked (planned) become exact instructions when their story is done, and each is tested before it's relied on.*

## Versions
- [Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`. Before 1.0.0, minor versions may change behaviour.
- Every release gets a Git tag (`v0.1.0`), a GitHub Release with the plain-language release notes, and a dated section in the [changelog](../CHANGELOG.md).

## How a release goes out
1. Work is merged into `dev` through pull requests and checked on the `dev` preview, including on a real phone.
2. A release pull request from `dev` to `main` updates the version, the changelog and the release notes. All required checks must pass.
3. **The owner merges it by hand.** Nobody else releases to production.
4. Vercel holds the production deploy until all four required checks (both CI jobs and both CodeQL jobs) pass on `main`, through Deployment Checks. If one fails, the live site stays as it was, and the fix goes through a new pull request. Merges before v0.1.0 carry no version or tag. Both halves were proven on 2026-11-09: a deploy was held when a check failed, and the next release went live once all four checks passed (see the [decision log](decisions.md#previews-and-the-deploy-gate-2026-11-09)).
5. The tag and GitHub Release are created, and the live site is checked.

## Database changes
- Migrations are generated by Drizzle, committed to the repo, and only move forward. A mistake is fixed with a new migration.
- **Expand/contract.** A change must work with both the previous and the new app version. Add a column or table first, release code that uses it, then remove the old one in a later release. Renaming in place is not allowed.
- Migrations run in CI against a throwaway database, then on the `dev` sandbox, before production.
- Before a production migration, a Neon snapshot (branch) of `main` is taken (planned).

Expand/contract is what keeps the app rollback safe: the previous version still works on the new schema.

## Rolling back a bad release
1. Vercel > the project > Deployments > the previous production deployment > **Instant Rollback** (planned, tested before v1.0.0).
2. Fix the problem through a new pull request, never by changing `main` directly.
3. If data was damaged, restore it (below).
4. Record what happened and the fix in the changelog.

## Backups and restore
- **Daily backup** (planned, before v0.1.0): a scheduled GitHub Action, at most once a day, runs `pg_dump` of the production database. It encrypts the dump with [age](https://age-encryption.org/) using a public key stored in the repo. The private key stays offline with the owner. The encrypted file is kept as a workflow artifact for 30 days. Nothing unencrypted leaves the runner.
- **Short-term:** Neon's point-in-time restore covers recent mistakes within its free-plan window.
- **Restore procedure** (planned): decrypt the dump, restore it into a new Neon branch, check it, then point production at it or copy the affected rows back. It's timed against the 1-hour target in [nfr.md](nfr.md).
- **Restore drill:** done before v0.1.0 and again before v1.0.0, with the date and time taken recorded here.
